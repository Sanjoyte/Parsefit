## 1. Status, scope and ownership

This is a small pnpm/strict-TypeScript monorepo plan: one universal Expo application, one separately deployable Fastify API, and four narrow shared packages. Web and Android are targets of the same application. A separate web application is not part of the approved layout.

| Exact status label | Meaning |
| --- | --- |
| EXISTING | Present before ARCH-DOCS. Does not imply application implementation or validation. |
| PLANNED | Absent at this stage. A milestone annotation describes when to create it, not authorization to create it now. |
| CREATED IN PART ARCH-DOCS | Created by this approved documentation task: only ARCHITECTURE.md and STRUCTURE.md. |
| CREATED IN PART COORD-DOCS | Created by the later owner-requested execution/agent-continuity documentation task; no application implementation implied. |
| CREATED IN PART README-DOC | Created by the owner-requested root README task; no application implementation implied. |
| CREATED IN PART SETUP-DOC | Created by the owner-requested setup-documentation task; no application implementation or environment provisioned. |
| CREATED IN PART AUDIT-DOCS | Approved audit plan and documentation-only audit report; no application implementation or runtime compatibility evidence. |

Milestones M0-M6 retain the analysis's meanings: feasibility, manual journals, workout/schedule, targets/aggregates, accounts/sync/privacy, vetted intelligence, website pilot. Later means separately approved post-MVP work. Files used by a prototype may begin at M0 with synthetic behavior and acquire full implementation later; that does not mean their production gate has passed.

Every tree entry below is annotated. The trees are maintained-source plans, not shell instructions or claims that dependencies/configuration exist. Create only files needed by the active milestone. Repository metadata internals, generated dependency trees and generated outputs are intentionally not enumerated. Update this document's statuses only when files actually exist, and record the creating part ID. Planned directories do not need placeholder files.

Feature directories acquire `screens/`, `components/`, `hooks/` and colocated component tests only where needed; these are conventions, not mandatory empty skeletons. Exact entry points are constrained by the route map above and the ownership table below. Share screen implementations between targets, with small platform-specific UI files only when semantics remain the same. Date/record IDs in fixed-route parameters avoid static generation of private dynamic record paths. Browser route parameters are untrusted and do not grant record access.

Durable repository implementations live under data; adapters implement the lower-level storage/runtime contracts. `application/ports.ts` owns use-case-facing interfaces; `data/storage-contract.ts` owns adapter-facing atomic operations. Composition is the only place allowed to select concrete web/native implementations. This prevents a misleading “universal repository” that secretly calls browser APIs.
